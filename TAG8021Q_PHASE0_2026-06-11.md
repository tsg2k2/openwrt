## QUESTION 1 — RTL9303 ingress "force PVID" classification

**VERDICT: SUPPORTED via the per-port PBVLAN mode field — `PBVLAN_MODE_ALL_PKT` (value 2)
in `RTL930X_VLAN_PORT_PB_VLAN` (0x82D8) forces port-based VID assignment for ALL ingress
packets including already-tagged ones. The mechanism exists in the register API of our
driver but is NEVER exercised (driver always uses `PBVLAN_MODE_UNTAG_AND_PRITAG`), so HW
behavior needs one live confirmation.**

### The mechanism

The mode enum, `RTL83XX/rtl-otto.h:901-910`:

```c
enum pbvlan_type  { PBVLAN_TYPE_INNER = 0, PBVLAN_TYPE_OUTER };
enum pbvlan_mode  {
        PBVLAN_MODE_UNTAG_AND_PRITAG = 0,   /* PVID applies to untagged + prio-tagged */
        PBVLAN_MODE_UNTAG_ONLY,             /* PVID applies to untagged only */
        PBVLAN_MODE_ALL_PKT,                /* PVID applies to ALL packets <- force PVID */
};
```

RTL930x implementation, `RTL83XX/rtl930x.c:2522-2536` — one 32-bit register per port at
`RTL930X_VLAN_PORT_PB_VLAN + (port << 2)` (base 0x82D8, `rtl-otto.h:84`):

- inner PVID mode: bits [1:0]; inner PVID: bits [13:2]
- outer PVID mode: bits [15:14]; outer PVID: bits [27:16]

```c
static void rtl930x_vlan_port_pvidmode_set(int port, enum pbvlan_type type, enum pbvlan_mode mode)
{
        if (type == PBVLAN_TYPE_INNER)
                sw_w32_mask(0x3, mode, RTL930X_VLAN_PORT_PB_VLAN + (port << 2));
        else
                sw_w32_mask(0x3 << 14, mode << 14, ...);
}
```

Exposed via ops `rtl-otto.h:1431-1432` (`vlan_port_pvidmode_set` / `vlan_port_pvid_set`),
wired at `rtl930x.c:2844-2845`.

Current usage — driver only ever sets the *non*-forcing mode, `RTL83XX/dsa.c:78-90`
(`rtldsa_vlan_set_pvid`): both inner and outer PVID set, both modes set to
`PBVLAN_MODE_UNTAG_AND_PRITAG`. **`PBVLAN_MODE_ALL_PKT` has zero callers** in the entire
realtek target — it is plumbed but untested.

### Related ingress/egress controls (the rest of the kit tag_8021q needs)

- **Ingress VLAN membership filter** (`IVC`-equivalent): `RTL930X_VLAN_PORT_IGR_FLTR`
  (0x83C0, `rtl-otto.h:85`), 2 bits/port — `IGR_FORWARD=0 / IGR_DROP=1 / IGR_TRAP=2`
  (`rtl-otto.h:1109-1113`, writer `rtl930x.c:2575-2579`). Driver semantics in
  `dsa.c:1552-1590` (`rtldsa_vlan_filtering`): filtering on → user ports `IGR_DROP`,
  CPU port `IGR_TRAP`; filtering off → `IGR_FORWARD`. For tag_8021q the user ports stay
  `IGR_FORWARD`, so membership filtering will not fight the forced PVID.
- **Forwarding tag basis**: `RTL930X_VLAN_PORT_FWD` (0x834C, `rtl-otto.h:306`) selects
  L2 forwarding on inner vs outer tag per port (`rtl930x.c:455-462`); setup forces
  inner-tag basis for all ports (`dsa.c:140-142`).
- **Egress tagging** (needed so the CPU port emits the classified VID as a real tag):
  - per-VLAN untagged-member table `rtl930x_vlan_set_untagged` (TBL_2),
    `rtl930x.c:445-452`;
  - per-port egress keep-tag override `rtl930x_vlan_port_keep_tag_set`
    (`RTL930X_VLAN_PORT_TAG_STS_CTRL`), `rtl930x.c:2513-2520`.
  So: CPU port = tagged member of every tag_8021q VLAN, user ports = untagged members
  of their own VLAN. Both knobs already exist.
- Our patch `package/kernel/kmod-rtl930x-spi/patches/08-vlan-stp-untagged-bridging.patch`
  currently pre-programs VLAN 1 with *all ports untagged* and patch
  `06-cpu-port-pvid.patch` + `13-vlan-unaware-bridge-vid.patch` hard-wire the
  "classify everything to VLAN 1" model. All three encode the old single-VLAN design and
  will be reworked/retired by the migration.

### What source alone cannot prove

Whether `ALL_PKT` mode (a) re-classifies a tagged frame to the PVID *and* (b) the original
tag is then replaced (not stacked) on tagged egress to the CPU port. Realtek SDK naming
("port-based VLAN for all packets") strongly implies yes, but no in-tree user exists.
**Live experiment:** set mode 2 + PVID on lan1 via the SPI regmap, ingress a frame tagged
with an unrelated VID from the .111 client, confirm (1) it still forwards, (2) the CPU
port copy carries the PVID (we have HW mirroring + tc tooling for exactly this, see
[[project-rtl9303-tc-mirror-offload]]).

## QUESTION 2 — what the OTTO tag actually carries / what we'd lose

**VERDICT: NOTHING of functional value is lost if the CPU only learns "source port".
The RX path parses exactly 3 things — ethertype, source port, reason — and the only
*consumer* beyond source port is `reason == 0` gating `offload_fwd_mark`. Every frame
class that arrives with a non-zero reason today (BPDU/LLDP/EAPOL traps) is link-local
traffic the bridge never forwards anyway. TX-side, the only per-packet metadata is the
destination portmask + IGNORE_STP, both of which tag_8021q replaces structurally.**

### RX parse inventory (`target/linux/qualcommax/files/net/dsa/tag_rtl_otto.c`, 195 lines)

| Field | Parsed at | Used? |
|---|---|---|
| EtherType 0x8899 | `tag_rtl_otto.c:142` | gate only (tag present?) |
| `proto` byte (0x04) | never validated on RX | ignored |
| `reason` (byte) | :151-152 | **yes** — `reason == RTL_OTTO_REASON_FORWARD (0)` → `dsa_default_offload_fwd_mark()` (:158-159). Non-zero (trapped) → mark NOT set → bridge would software-forward |
| `cpu_tag[0]` bits[13:8] = source port | :149-150 | **yes** — `dsa_conduit_find_user()` (:154) |
| `cpu_tag[1..7]` (qid, etc.) | not parsed | ignored |
| no-tag fallback | :167-178 | delivers untagged frames to the first user port (bring-up safety net only) |

### TX build inventory (`tag_rtl_otto.c:84-115`)

- `cpu_tag[0] = 0x8000` marker; `cpu_tag[1] = FWD_PHYSICAL | IGNORE_STP` (:102-105);
  `cpu_tag[4..7]` = 64-bit destination portmask (:109-112).
- Required because with `MAC_L2_CPU_PORT_CTRL` (0xc70c) bit0 set, the switch resolves
  unicast destinations from the tag's dp mask (comment block :69-80).

### Driver-side dependencies on per-packet tag metadata

- **The CPU-port-designate bit itself** — `package/kernel/kmod-rtl930x-spi/src/rtl930x_spi.c:142-145`
  (`RTL930X_MAC_L2_CPU_PORT_CTRL 0xc70c`), re-assert worker :660-700, netdev-notifier
  re-fire :706-718, init :936-944; plus
  `package/kernel/kmod-rtl930x-spi/patches/09-cpu-port-wire-tag.patch` (writes 0xc70c in
  `rtldsa_93xx_setup`). For tag_8021q this bit must be **0** (raw egress, no inline tag)
  and the re-assert worker must be disabled/gated — otherwise the switch prepends 0x8899
  on every CPU-bound frame and breaks the 802.1Q parse.
- **Traps that produce non-zero reason codes today** (consumers of "reason reaches CPU"):
  - BPDU + LLDP `TRAP2CPU` for every port: `RTL83XX/dsa.c:145-155`, installed at
    :206-207 (83xx) and :272-273 (93xx setup).
  - EAPOL trap: `RTL83XX/common.c:1698-1699`.
  - `vlan_filtering=1` CPU-port `IGR_TRAP`: `dsa.c:1574`.
  - tc-flower `FLOW_ACTION_TRAP`: `RTL83XX/tc.c:159-165`.
  None of these *configure* anything based on the reason value; they only cause frames to
  reach the CPU. The reason byte's sole effect is the fwd-mark gate in the tagger.
- **Nothing else.** `grep offload_fwd_mark|source_port|reason` over the driver sources
  finds no other consumer; IGMP/MLD reports are NOT trapped on 930x (no IGMP trap config
  exists — reports reach the CPU as ordinary forwarded/flooded multicast, reason 0), so
  our HW IGMP snooping never depended on reason codes either.

### Residual deltas under tag_8021q (cosmetic → minor)

1. Trapped frames (BPDU/LLDP/EAPOL/tc-trap) will get `offload_fwd_mark = 1` like
   everything else (`tag_vsc73xx_8021q.c` calls `dsa_default_offload_fwd_mark()`
   unconditionally — `KSRC/net/dsa/tag_vsc73xx_8021q.c:50`). For BPDU/LLDP/EAPOL this is
   moot (link-local, bridge never forwards). For a future tc `trap` rule on a bridged
   port, the bridge would decline to software-forward the trapped copy — same as today
   actually *only if* the reason was 0; mark it as a behavioral footnote, not a loss.
2. TX `IGNORE_STP` disappears: CPU-injected frames become subject to normal egress STP
   state. STP is off in our deployment; if ever enabled, BPDU TX to a BLOCKING port needs
   verification (vsc73xx upstream lives with the same constraint).
3. Directed (standalone-port) TX changes from explicit portmask to "VID whose only
   members are {target port, CPU}" — functionally equivalent, but relies on the switch
   flooding an unknown-DA frame inside that VLAN to the single member. Same mechanism
   vsc73xx uses.

## QUESTION 3 — HPPE flow-table VLAN ops (PPE HW NAT go/no-go)

**VERDICT: YES for routed/NAT flows, with the VLAN work done by the NEXTHOP table, not
the flow entry. NO for bridge-type flows — the per-flow `vlan_fmt`/`svlan_fmt`/`cvlan_fmt`
fields are APPE-only (ipq95xx) and on HPPE silicon those bits are literally reserved.
The flow lookup KEY contains no VLAN on HPPE, so ingress VLAN is structurally ignored by
flow matching; ingress VID only matters upstream of the flow engine (VLAN→VSI→L3IF), and
that mapping is fully programmable. Net: PPE HW NAT offload of LAN↔WAN traffic over a
tag_8021q LAN leg is feasible.**

### Flow entry fields (`SSDK/include/fal/fal_flow.h:92-136`, `fal_flow_entry_t`)

- fwd types `fal_flow_fwd_type_t` (:46-54): `FORWARD/SNAT/DNAT/ROUTE/BRIDGE/DROP/RDT_TO_CPU`.
- VLAN-relevant fields, **explicitly marked APPE**:
  ```c
  a_bool_t vlan_fmt_valid; /* egress with vlan format of bridge, added for ipq95xx */
  a_bool_t svlan_fmt;      /* ... added for ipq95xx */            (fal_flow.h:127-129)
  a_bool_t cvlan_fmt;
  ```
- `l2_vpn_en` ("enable vsi as flow key", `fal_flow.h:160-161`) is also "added for
  ipq95xx" → on HPPE the key cannot even opt in to VLAN/VSI.

### What `adpt_hppe_flow_entry_host_op_add`/`..._add` actually programs on HPPE

`SSDK/src/adpt/hppe/adpt_hppe_flow.c:288-299` (pattern repeated for all 4 entry types at
:339-350, :396-407, :445-456, and in `adpt_hppe_flow_entry_add` proper from :1924):

```c
} else if (flow_entry->fwd_type == FAL_FLOW_BRIDGE) {
        entry.bf1.port_vp2 = flow_entry->bridge_port;
#if defined(APPE)
        entry.bf1.vlan_fmt_valid = flow_entry->vlan_fmt_valid;   /* NOT compiled for HPPE */
        entry.bf1.svlan_fmt      = flow_entry->svlan_fmt;
        entry.bf1.cvlan_fmt      = flow_entry->cvlan_fmt;
#endif
```

Register-level confirmation, `SSDK/include/hsl/hppe/hppe_flow_reg.h:936-960`
(`struct in_flow_tbl_1`): after `port_vp2:8`, HPPE has `_reserved0:20` where APPE has
`vlan_fmt_valid:1 / svlan_fmt:1 / cvlan_fmt:1 / ...`. **The IPQ8074 flow table has no
VLAN-format bits in silicon.**

Key fields programmed (IPv4 5-tuple, `adpt_hppe_flow.c:300-317`): host_addr index,
protocol, IP, `l4_sport`, `l4_dport` — **no VID anywhere in the key**. `src_l3_if_valid`
/`src_l3_if` (:275-276) is an *optional* source-interface check — leave invalid to make
the flow hit regardless of ingress interface.

### Where VLAN ops DO live on HPPE: the nexthop

`SSDK/include/fal/fal_ip.h:282-296`, `fal_ip_nexthop_t`:

```c
a_uint8_t  stag_fmt;  /* 0: untag 1: tagged */
a_uint16_t svid;
a_int8_t   ctag_fmt;  /* 0: untag 1: tagged */
a_uint16_t cvid;
fal_mac_addr_t mac_addr;
```

Programmed for HPPE **without any APPE guard** in
`SSDK/src/adpt/hppe/adpt_hppe_ip.c:1429-1459` (`adpt_hppe_ip_nexthop_set`,
IN_NEXTHOP_TBL): `stag_fmt/svid/ctag_fmt/cvid` at :1446-1449. SNAT/DNAT/ROUTE flows
reference nexthops (`adpt_hppe_flow.c:278-287`: `next_hop1/next_hop2/next_hop3` +
`port_vp1`), so **a NAT flow whose egress is a LAN port can push a C-tag with an
arbitrary VID (the tag_8021q TX VID of the destination port) and rewrite the DMAC, per
flow** — exactly what the migration needs for the PPE→RTL9303 direction.

### Ingress side (LAN→WAN): mapping tag_8021q RX VIDs into the L3 pipeline

- Ingress VLAN → VSI translation exists on HPPE: XLT rule/action tables in
  `SSDK/src/adpt/hppe/adpt_hppe_portvlan.c` — rule write `hppe_xlt_rule_tbl_set` (:342),
  action with `vsi_cmd/vsi` (:375-376); egress XLT at :410-414.
- VSI → L3 interface: `adpt_hppe_ip_vsi_intf_set` (`adpt_hppe_ip.c:957`); per-port
  fallback `adpt_hppe_ip_port_intf_set` (:390).
- So N per-port RX VIDs can be normalized to one VSI (single LAN L3IF) or given one
  L3IF each; the flow key doesn't care either way.
- Note: `fal_intf_mac_entry_t` has `vid_low/vid_high` (`fal_ip.h:146-155`) but no HPPE
  adpt consumes it (grep over `SSDK/src/adpt/hppe/*.c` is empty) — that's legacy ISIS
  API; do not plan around it.

### Caveat

Bridge-type flow acceleration (`FAL_FLOW_BRIDGE`) cannot retag on HPPE — irrelevant for
us because LAN↔LAN never reaches the PPE (RTL9303 switches it in hardware), and LAN↔WAN
is routed/NAT (= nexthop path). Whether the PPE parser accepts TPID 0x8100 on the EDMA
ingress by default (vs needing `fal_global_qinq`/TPID config) is a one-register check at
bring-up, not a design risk.

## QUESTION 4 — `change_tag_protocol` pattern, and where it lands in our driver

**VERDICT: WELL-TRODDEN PATH with two reference implementations in our kernel tree:
felix (runtime-switchable, TCAM-based precise RX) and vsc73xx (fixed 8021q protocol,
port-VLAN-membership based — the closer model for RTL930x). Required hooks:
`.change_tag_protocol` (only if runtime switching is wanted), `.tag_8021q_vlan_add/del`
(mandatory), `dsa_tag_8021q_register/unregister` from setup/teardown paths, plus a tiny
tagger module with a new `DSA_TAG_PROTO_*` value. One CRITICAL incompatibility found:
tag_8021q's VID encoding has a 4-bit port field and our port indices are 8/20/24/25 —
ports 8 and 24 COLLIDE. See Phase-1 implications.**

### The felix pattern (runtime protocol switching) — `KSRC/drivers/net/dsa/ocelot/felix.c`

- `felix_change_tag_protocol` (:755-800): maps proto → a `felix_tag_proto_ops` vtable
  (NPI vs 8021q, :561-566 / :667-672); sequencing = `new->setup()` →
  migrate shared state (`felix_tag_proto_setup_shared` :732-749: MDB migration, trap
  destinations, host-flood masks) → `old->teardown()`. Rollback-safe (:796-799).
- `felix_tag_8021q_setup` (:568-622): `dsa_tag_8021q_register(ds, htons(ETH_P_8021AD))`
  (:574), then per-port HW reconfig (8021q-CPU assignment :578-583, BPDU redirect
  disable :585-598, CPU-queue drain :607-609, `ds->untag_vlan_aware_bridge_pvid = true`
  :619). Teardown mirrors it and calls `dsa_tag_8021q_unregister` (:644).
- `felix_tag_8021q_vlan_add/del` (:270-331): felix implements the VLANs as **TCAM rules**
  — ES0 push-VID-toward-CPU per (user port, CPU port) for RX (:101-148), IS1 pop + IS2
  redirect for TX (:172-237) — skipping CPU-port calls entirely (:281-282).
- ops wiring: `.change_tag_protocol` at :2233, `.tag_8021q_vlan_add/del` at :2300-2301;
  initial protocol applied by calling `felix_change_tag_protocol` from `.setup`
  (:1727).

### The vsc73xx pattern (fixed tag_8021q, port-VLAN-membership) — `KSRC/drivers/net/dsa/vitesse-vsc73xx-core.c`

- `get_tag_protocol` permanently returns `DSA_TAG_PROTO_VSC73XX_8021Q` (:699); **no
  `.change_tag_protocol`** — protocol is fixed, infra registered once in `.setup`
  (`dsa_tag_8021q_register(ds, htons(ETH_P_8021Q))` under rtnl, :944-946) and
  unregistered in `.teardown` (:953-955).
- `vsc73xx_tag_8021q_vlan_add/del` (:1747-1797): commit the tag_8021q VID into the real
  VLAN table + conditionally commit it as the port's PVID, arbitrated against
  bridge-VLAN PVIDs by `vsc73xx_vlan_commit_pvid` (:1400-1413) depending on
  `dsa_port_is_vlan_filtering()`. This PVID-arbitration state machine is the part our
  driver must replicate.

### Core infrastructure — `KSRC/net/dsa/tag_8021q.c`

- VID layout (:15-64): `RSV[11:10]=3 | VBID_hi[9] | SWITCH_ID[8:6] | VBID_lo[5:4] |`
  **`PORT[3:0]`** — `DSA_8021Q_PORT_MASK GENMASK(3, 0)` (:62). Range 3072-4095.
- `dsa_tag_8021q_standalone_vid(dp)` (:92-97) = RSV | SWITCH_ID | PORT;
  `dsa_tag_8021q_bridge_vid(bridge_num)` (:80-87) = RSV | VBID.
- `dsa_tag_8021q_register` (:418-444) → `dsa_tag_8021q_port_setup` per user port
  (:339-367): installs the standalone VID via the driver's `.tag_8021q_vlan_add`
  (user port: `BRIDGE_VLAN_INFO_UNTAGGED | PVID` flags, CPU/DSA ports: plain+refcounted,
  :231-244) and adds the VID to the **conduit's RX filter** (`vlan_vid_add`, :364).
- Bridge join/leave helpers for the port-membership scheme (:269-336): on join, the
  per-port standalone VID is **replaced by the shared bridge VID** (precise source-port
  info is lost; the big comment at :269-287 spells out the TCAM vs PVID tradeoff), and
  `*tx_fwd_offload = true` (:308).
- RX decode `dsa_8021q_rcv` (:532-588) and `dsa_tag_8021q_find_user` (:502-514):
  precise (vbid==0) → `dsa_conduit_find_user`; bridged (vbid>=1) →
  `dsa_tag_8021q_find_port_by_vbid` which returns the **first** forwarding port of that
  bridge (:484-497) — imprecise by design.
- tag_8021q.c is compiled into `dsa_core` unconditionally in this tree
  (`KSRC/net/dsa/Makefile:9-18`) — no extra Kconfig needed for the core.

### Tagger module + protocol selection plumbing

- Minimal tagger = ~70 lines, see `KSRC/net/dsa/tag_vsc73xx_8021q.c`: xmit picks
  standalone vs bridge TX VID by `skb->offload_fwd_mark` + `br_vlan_enabled()` (:12-33),
  rcv = `dsa_8021q_rcv` + `dsa_tag_8021q_find_user` + unconditional fwd-mark (:36-53),
  `needed_headroom = VLAN_HLEN`, `promisc_on_conduit = true`,
  `MODULE_ALIAS_DSA_TAG_DRIVER(proto, name)` (:68).
- Proto enum: we already maintain the pattern —
  `target/linux/qualcommax/patches-6.12/0918-net-dsa-add-rtl-otto-tag-driver.patch` adds
  `DSA_TAG_PROTO_RTL_OTTO_VALUE 32` to `include/net/dsa.h` (tree already has
  `MXL862_8021Q = 31`); a new `DSA_TAG_PROTO_RTL_OTTO_8021Q = 33` goes in the same patch,
  and the tagger .c into `target/linux/qualcommax/files/net/dsa/` + Makefile hook.
- Selection: default comes from `ds->ops->get_tag_protocol`
  (`KSRC/net/dsa/dsa.c:1127-1150`); DT override `dsa-tag-protocol` property on the CPU
  port (:1263, handled :1174-1190, requires the driver to have `.change_tag_protocol`
  :1175-1178); runtime override via sysfs `/sys/class/net/<conduit>/dsa/tagging`
  (`KSRC/net/dsa/conduit.c:280-337` → `dsa_tree_change_tag_proto`, `dsa.c:981-1025`,
  which requires **conduit + all user ports administratively down** :997-1003).
  At probe, `ds->ops->change_tag_protocol` is only invoked when the chosen proto differs
  from the driver default (`dsa.c:568-584`); module auto-load via
  `request_module("dsa_tag-id-%d")` (`KSRC/net/dsa/tag.c:203-209`).

### Mapping onto our rtl930x-spi driver

- `get_tag_protocol`: `RTL83XX/dsa.c:68-76` (`rtldsa_get_tag_protocol`, hardcoded
  `DSA_TAG_PROTO_RTL_OTTO`).
- ops struct: `rtldsa_93xx_switch_ops`, `RTL83XX/dsa.c:2708-2763` — currently has
  **no** `.change_tag_protocol`, `.tag_8021q_vlan_add`, or `.tag_8021q_vlan_del`; the new
  hooks slot in here (and the 8021q register/unregister into `rtldsa_93xx_setup`,
  `dsa.c:235-291`, if we go vsc73xx-style fixed-protocol — the recommended first step;
  felix-style runtime flip can come later since our sessions ride the WAN, not the
  conduit).
- HW reconfig on flip to 8021q (the equivalent of felix's :578-598 block):
  1. `0xc70c` bit0 = 0 + neuter the re-assert worker
     (`src/rtl930x_spi.c:660-718,936-944`, patch 09);
  2. per-port: PVID = tag_8021q VID, pvidmode = `PBVLAN_MODE_ALL_PKT` (Q1);
  3. per-VLAN: membership {port, CPU}, port untagged, CPU tagged
     (`vlan_set_tagged`/`vlan_set_untagged`/`keep_tag`);
  4. retire patches 06/08/13's VLAN-1-everything model (and the
     `rtldsa_bridge_vid()` vid0→1 FDB/MDB remap becomes "remap to the port/bridge
     tag_8021q VID" instead).

## Phase-1 implications (discoveries that change/de-risk the plan)

1. **★ BLOCKER FOUND EARLY — tag_8021q port-field collision.** `DSA_8021Q_PORT_MASK` is
   4 bits (`KSRC/net/dsa/tag_8021q.c:62`); our DTS port indices are 8, 20, 24, 25
   (`target/linux/qualcommax/dts/ipq8072-cr1000a.dts:233-280`). `24 & 0xF == 8` →
   **lan1 and lan10g get the SAME standalone VID (3080)**; ports 20→"4", 25→"9" are
   merely wrong. Vanilla core is unusable as-is. Options:
   a) small kernel patch widening PORT into the (useless for us, single-switch)
      SWITCH_ID bits VID[8:6] — e.g. PORT[4]=VID[6] gives 5 bits, covers port 25; we
      already carry dsa.h patches (0918) so this is cheap and contained;
   b) custom tagger + driver-managed VLANs bypassing `dsa_tag_8021q_register` entirely
      (lose the conduit `vlan_vid_add` and refcounting plumbing — more code, no core
      divergence).
   Recommend (a).

2. **Imprecise bridged RX would silently break our HW IGMP/MDB offload.** The core's
   port-membership bridge model replaces per-port VIDs with one bridge VID
   (`tag_8021q.c:288-312`), and `dsa_tag_8021q_find_port_by_vbid` attributes ALL bridged
   RX to the *first* forwarding bridge port (:484-497). IGMP reports would be logged
   against the wrong port → wrong MDB portmasks ([[project-igmp-snooping-hw-offload]]
   pruning regresses). **Mitigation that RTL930x supports:** keep per-port standalone
   VIDs even while bridged (don't adopt `dsa_tag_8021q_bridge_join`) and make HW
   bridging work across the per-port VLANs via shared-FID (SVL) learning — the VLAN
   info struct already exposes `fid` + `hash_uc_fid/hash_mc_fid` ("build L2 hash with
   FID instead of VID", `RTL83XX/dsa.c:112-115`); give all tag_8021q VLANs of one bridge
   the same FID and hash on FID. This is the felix-precise outcome without TCAM, and it
   also keeps RX precise for the PPE side.

3. **PPE NAT offload design is confirmed viable on HPPE** (Q3): VLAN-agnostic flow key +
   per-nexthop `ctag_fmt/cvid` push (`adpt_hppe_ip.c:1446-1449`) handles the egress
   retag toward each LAN port; ingress per-port VIDs map via XLT→VSI→L3IF. The
   APPE-only per-flow vlan_fmt limitation only affects bridge flows, which never hit the
   PPE in our topology. This resolves the "NSS-vs-multi-NAPI" backlog question's
   offload-path half: nothing in the flow engine blocks the tag_8021q plan.

4. **Register the 8021q context with `ETH_P_8021Q`** (vsc73xx style, not felix's
   `ETH_P_8021AD`) so the PPE sees a standard C-tag it can parse/hash. Verify EDMA/PPE
   TPID acceptance on dp5 ingress at bring-up (one register check, low risk).

5. **`PBVLAN_MODE_ALL_PKT` is plumbed but has zero in-tree users** — the single biggest
   HW unknown. The one live experiment that gates everything: force-PVID a user port,
   inject a foreign-VID-tagged frame, confirm classification + CPU-port retag (Q1,
   experiment described there). Everything else in the plan has existing in-tree
   precedent.

6. **Reason-code loss is a non-issue** (Q2): its only consumer is the fwd-mark gate, and
   every currently-trapped class is link-local. Two footnotes to carry into testing:
   trapped frames must still egress the CPU port *with* the VLAN tag (so source port
   stays identifiable) — unverified in source, needs the Q1 experiment to also send one
   BPDU; and `IGNORE_STP` TX bypass disappears (moot while STP is off).

7. **Sequencing freebie:** since we control the default via `get_tag_protocol`, Phase 1
   can ship vsc73xx-style (fixed 8021q protocol, no `.change_tag_protocol`) and we keep
   the old tagger one `git revert` away — no need to implement runtime flipping or the
   felix migration machinery (`felix_tag_proto_setup_shared`-equivalent for MDB/trap
   migration) unless we want A/B testing without reflash. If we DO want it: sysfs flip
   requires conduit+user ports down (`dsa.c:997-1003`) — our SSH rides WAN, so it's
   safe to do remotely.

8. **Cleanup inventory bound to this migration:** patch 06 (CPU-port PVID), patch 08
   (VLAN-1 all-untagged init), patch 13 (vid0→1 FDB/MDB remap), patch 09 + the
   `rtl930x_spi.c` 0xc70c worker (:660-718) all encode the old model and must be
   reworked/gated; the tagger's untagged-frame fallback (`tag_rtl_otto.c:167-178`)
   has a cleaner equivalent in `dsa_find_designated_bridge_port_by_vid`.

## Phase-1 design decision: the port-field collision fix (added after review)

Fix the 4-bit PORT collision (ports 8/24) by encoding the port's ordinal
position among the switch's user ports (sorted by index: 8->0, 20->1,
24->2, 25->3) instead of the raw dp->index. Properties:

- Board-agnostic with no new DT bindings: the mapping derives from the
  ports node every board already has, and works for any switch with up
  to 16 ports in use regardless of numbering sparseness.
- Bit-identical for all existing upstream users (sja1105/felix/vsc73xx
  number ports densely from 0, so position == index) - a pure
  generalization, upstreamable rather than a maintained fork.
- Contained: ~40-60 lines in net/dsa/tag_8021q.c - a position helper in
  dsa_tag_8021q_standalone_vid() and position->port translation in
  dsa_tag_8021q_find_user() (which already holds the switch tree).
  Taggers and drivers are unaffected.

Out of scope for phase 1: an optional per-port VID override property
(only needed for >16 used ports, e.g. RTL9313-class, where 4 bits are
structurally exhausted and position encoding must additionally borrow
SWITCH_ID bits).
